# 课程 SAFE-05：电池系统网络安全——功能安全的"前置守门员"

> 对应节点 `SAFE-05`（[../domains/02-安全设计.md](../domains/02-安全设计.md)）｜ 前置：[SAFE-01](SAFE-01-功能安全流程.md)、[SYS-04](SYS-04-整车网络节点.md) ｜ 预计用时 60 min
> 数字规则：法规生效时间点以官方文本为准（本课标注待核对）；示例数字均为**教学示意值**。

## 1. 为什么网络安全能"击穿"功能安全

功能安全假设失效是**随机的**（元件老化、干扰）；网络安全面对的失效是**故意的、智能的、找最弱点的**。攻击者让 BMS 误动作（伪造过充、屏蔽保护），ISO 26262 的随机失效分析完全覆盖不了这种威胁。节点约束：**攻击面含 OBD/OTA/充电口/无线链路；需 CSMS 与入侵检测。** 法规已强制：UN R155（S-14）要求车辆型式认证配备 CSMS（Cybersecurity Management System，网络安全管理体系）；UN R156（S-15）管软件升级安全。

## 2. 机制展开：攻击面与 TARA

**（1）BMS 的攻击面清单**（对应节点约束）

| 攻击面 | 入口技术 | 典型威胁 |
|---|---|---|
| OBD 诊断口 | UDS（ISO 14229-1，S-09）安全访问服务 | 弱密钥被破解 → 改阈值/刷固件 |
| OTA 升级通道 | UN R156（S-15）要求的安全升级 | 伪造固件、降级攻击（刷回旧漏洞版本） |
| 充电口 | GB/T 27930（S-05）/ ISO 15118（S-10） | 伪造充电机/BMS 报文，篡改功率限值 |
| 无线链路 | wBMS 射频（`ARCH-W`）、TSP 云端通道 | 中间人、重放、密钥泄露 |
| 车内总线 | CAN 注入（`SYS-04`） | 从被攻破的娱乐域横向打到动力域 |

**（2）TARA（Threat Analysis and Risk Assessment，威胁分析与风险评估；ISO/SAE 21434:2021，S-08）**

流程：资产识别 → 威胁场景识别 → 影响评级（safety/financial/operational/privacy 四维）→ 攻击路径分析 → 攻击可行性评估（要素含耗时、专业知识、装备、窗口期）→ 风险值 → 处置选项（避免/降低/分担/保留）→ 残余风险记录。与 HARA 的关系：**TARA 的 safety 影响喂给功能安全，形成"网络安全 → 功能安全"传导链**。

**（3）纵深防御机制（由外到内逐层）**：安全启动（secure boot，固件签名链）→ 访问控制（UDS 安全访问，失败锁定）→ 通信保护（E2E + 报文认证）→ 域隔离/防火墙 → 入侵检测（IDS，节点约束）→ 安全 OTA（R156）。

## 3. 工程案例推演：充电限值信号被伪造的 TARA

场景：攻击者介入充电桩与车辆之间，伪造充电功率限值报文，诱使 BMS 接受超限充电电流。

| TARA 步骤 | 本例内容 |
|---|---|
| 资产 | BMS↔充电机的功率限值报文（GB/T 27930 链路） |
| 威胁场景 | 篡改/伪造（spoofing/tampering）限值报文 |
| 影响评级 | safety：过充 → 热失控（对应 SG-01，ASIL D）——**高** |
| 攻击路径 | 拆解/仿冒充电桩侧接口 → 注入伪造报文 |
| 攻击可行性 | 需专用装备+协议知识+物理接近；窗口期长（充电 30~60 min）——中等 |
| 风险值 | 高（safety 影响极大） |
| 处置 | 充电报文加源认证/会话密钥；BMS 侧限值合理性自检（对照自身电压/温度状态） |
| 残余风险 | 记录并纳入监控（IDS 规则：限值突变报文告警） |

配套数字（教学示意值）：UDS 安全访问连续 3 次密钥错误 → 锁定延迟 10 s；诊断会话超时 5 s。这两个数字同时是**功能安全相关参数**——保护功能可被诊断服务修改，诊断写操作需受 ASIL 约束。

## 4. 工程实态

- 法规节奏：**UN R155 生效时间线已核实（2026-11-06，UNECE 官方文本 R155e.pdf，S-60）**——新车型型式认证自 **2022-07** 强制，**所有新产车辆**自 **2024-07** 强制（此前生产的旧型式有过渡条款）——出口欧盟车型必须持 CSMS 证书；
- **EU CRA 叠加（2026-11-17 核实，S-74）**：Cyber Resilience Act 于 2024-12-10 生效，**2026-09-11 起漏洞/事件上报义务已生效**（24 h/72 h 上报 ENISA），**2027-12-11 全面适用**——含数字元件产品需安全设计、SBOM、漏洞处理，CE 标志成为合规前置。对 BESS/联网 BMS 产品出口欧盟是 R155 之外的**第二层合规**；
- 诊断层：UDS **Authentication 服务（0x29）已核实（2026-11-06，S-61）**——由 ISO 14229-1:2020 引入，支持 PKI 证书 + 非对称加密认证，是对 0x27 的现代化补充；AUTOSAR RS_Diagnostics（R20-11）已要求支持；量产仍以 0x27 为主、0x29 依赖 PKI 基础设施落地（观点级）；
- 组织层：CSMS 覆盖全生命周期（开发 → 生产 → 后生产），OEM 设 VSOC（Vehicle Security Operations Center，车辆安全运营中心）做持续监控与漏洞响应（节点约束的"持续"含义）；
- 项目层：TARA 在概念阶段与 HARA 并行互喂；渗透测试作为验证手段；
- 供应链：ISO/SAE 21434 专门规范分布式网络安全活动（OEM↔Tier1↔Tier2 的接口协议）。

## 5. 常见误区

1. "网络安全=加密"——加密只护保密性；对 BMS 致命的是完整性（改限值）与可用性（屏蔽报警）；
2. 只防边界不防横向——车内 CAN 是平面网络，一点突破处处可达，必须域隔离；
3. 当一次性项目做——漏洞持续出现，CSMS/IDS/漏洞管理是常设机制（节点约束）；
4. 安全功能自身不设防——IDS/防火墙若可被关闭，就成了新的攻击面；它们的失效同样要进安全分析。

## 6. 自测

**Q1**：为什么 ISO 26262 覆盖不了网络安全威胁？
**Q2**：TARA 与 HARA 的衔接点在哪里？
**Q3**：BMS 诊断服务的"写阈值"操作，网络安全上要注意什么？

<details><summary>答案</summary>

- Q1：26262 的风险模型基于随机失效与无意缺陷，攻击是故意的、自适应的、寻找最弱点的——需要威胁建模（TARA）与对抗性思维；HARA/FTA/FMEA 不建模"攻击者"这个角色。
- Q2：TARA 影响评级中的 safety 维度：网络威胁若能引发安全危害（如伪造限值 → 过充），防护需求要与 HARA 的安全目标/ASIL 对齐，形成传导链（本例对应 SG-01）。
- Q3：写操作必须经安全访问且受 ASIL 约束；密钥强度/失败锁定防暴力破解；阈值写入后需合理性自检（防越权写入危险值）；写入行为留痕（审计日志）。
</details>
