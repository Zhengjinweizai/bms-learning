# 课程 SAFE-02：HARA 与安全目标——给危害定价

> 对应节点 `SAFE-02`（[../domains/02-安全设计.md](../domains/02-安全设计.md)）｜ 前置：[SAFE-01](SAFE-01-功能安全流程.md) ｜ 预计用时 60 min
> 数字规则：S/E/C 类别定义与定级表源自 ISO 26262-3:2018（S-07）；案例评分全部为**教学示意值**（实际评分按各主机厂评分基准执行）。

## 1. 为什么 HARA 是安全工作的入口

节点约束给死两条：**场景需覆盖行驶/充电/静止三态；安全目标需量化（如预警时间）。** HARA（Hazard Analysis and Risk Assessment，危害分析与风险评估）是功能安全体系唯一的风险入口：不经过 HARA 的功能没有 ASIL；没有 ASIL 的需求不知道按多严的标准开发。`README` 下一批候选里点名"拿一个过充场景走完整 HARA"——本课第 3 节就是这个案例。

## 2. 机制展开：S、E、C 三因子与定级表

HARA 对每个"运行场景 × 危害事件"组合打三个分（类别定义源自 ISO 26262-3:2018）：

- **S（Severity，严重度）**：潜在伤害的严重程度。S0 无伤 → S1 轻/中度伤 → S2 重度伤（可能幸存）→ S3 危及生命（生存不确定）/致命；
- **E（Exposure，暴露率）**：处于该运行场景的概率。E0 极低 → E1 很低 → E2 低 → E3 中 → E4 高（按单位时间/里程出现概率分级）；
- **C（Controllability，可控性）**：驾驶员/涉险人员避免伤害的能力。C0 总体可控 → C1 简单可控 → C2 正常可控 → C3 难以控制/不可控。

**三因子查表得 ASIL**（ISO 26262-3 的定级表；此处列 S3 行示意完整逻辑，其余行规则同构——S/E/C 越高 ASIL 越高；完整表以标准原文为准）：

| S | E | C1 | C2 | C3 |
|---|---|---|---|---|
| S3 | E2 | QM | A | B |
| S3 | E3 | A | B | C |
| S3 | E4 | B | C | D |

**安全目标（Safety Goal）**：HARA 的产出——针对危害事件的**顶层定性目标**（避免什么状态），随附最严 ASIL；量化要求（预警时间等）在其后的技术安全需求落地（节点约束"量化"的正确落点，见 `SYS-03`）。

## 3. 工程案例推演：过充场景的完整 HARA 表

**同一危害机理（电芯过充 → 热失控 → 起火/爆炸），三个运行场景分别评分**（评分全为教学示意值）：

| 编号 | 运行场景 | 危害事件 | S | E | C | ASIL |
|---|---|---|---|---|---|---|
| H-01 | 直流快充（常无人值守） | 充电机未响应停止请求，持续过充至热失控 | S3 | E4（快充高频使用） | C3（人员无法及时干预） | **D** |
| H-02 | 行驶中 | 能量回收叠加致瞬时过压 | S3 | E3（满电+大回收+低温等严苛组合占比低，示意） | C2（驾驶员可减速并靠边） | B |
| H-03 | 交流慢充（夜间驻车） | 慢充控制异常致缓慢过充 | S3 | E3（低频） | C3（无人值守） | C |

推演要点：
1. **三态覆盖是检查表**：充电（H-01/H-03）与行驶（H-02）已覆盖；静止不充电态的相关危害（如绝缘失效，`HV-03`）另行分析——三态不是"恰好三条"，是防遗漏的最低要求；
2. **同一机理、不同 ASIL**：过充保护功能的开发严格度由**最严场景支配**（H-01 → D）。低 ASIL 场景并非无用：它们构成不同工况下的纵深条件；
3. **安全目标产出**：SG-01"防止任一电芯超过充电电压上限"（ASIL D，支配级）→ 交给 `SAFE-03` 做分解、`SYS-03` 建溯源链、`SAFE-04` 做时间预算；
4. **E 评分的纪律**：E4/E3 的判定要有场景频率依据（快充频次统计/工况数据），拍脑袋评分是审核追问的重灾区；C 评分同理需要可控性论证。

## 4. 工程实态

- 各主机厂维护自己的**评分基准表**（把 S/E/C 类别定义落成本公司判据与数据来源），供应商按基准表做 HARA 再交评审；
- HARA 场景库与 `DEV-06` 场景库复用：真实工况数据反哺 E 评分；
- 一个电池系统的 HARA 通常产出数十条安全目标（过充/过放/过温/过流/绝缘/碰撞后断电等，示意量级）；
- 诚实局限：HARA 的主观成分不可消除（尤其 C 评分），靠评审与数据压低不确定性，而非消除。

## 5. 常见误区

1. 把 ASIL 赋给部件（"这个 MCU 是 ASIL D"）——ASIL 是危害事件的属性，部件经由承载安全需求获得等级；
2. 安全目标写成解决方案（"应断开接触器"）——那是 FSC 层的事；安全目标只说"避免什么状态"；
3. 场景只覆盖行驶态——充电/驻车态常评分更严（无人值守 → C3），漏场景=漏最严 ASIL；
4. E/C 评分无依据留痕——审核追问"凭什么 E4"，答不上来整张表作废。

## 6. 自测

**Q1**：S3 + E4 + C2 查表得什么 ASIL？
**Q2**：为什么过充的快充场景通常比行驶场景评分更严？
**Q3**：安全目标写成"应在检测到过充后 200 ms 内断开接触器"有什么问题？

<details><summary>答案</summary>

- Q1：**C**（S3 行、E4 列、C2 → C）。
- Q2：快充高频发生（E 高）且常无人值守（C 差），两项同时恶化；行驶场景驾驶员在场可控性较好，且"满电+大回收+低温"等严苛组合占比低（示意）。
- Q3：这是技术安全需求（TSR）的写法——把解决方案（断接触器）和时间参数写进了顶层目标；安全目标应定性描述要避免的危害状态（"防止电芯过充"），时间预算在其下层落地（SYS-03）。
</details>
