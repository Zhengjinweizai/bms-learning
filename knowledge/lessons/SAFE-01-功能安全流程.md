# 课程 SAFE-01：功能安全流程 ISO 26262——安全是属性不是功能

> 对应节点 `SAFE-01`（[../domains/02-安全设计.md](../domains/02-安全设计.md)）｜ 前置：[SYS-03](SYS-03-需求管理.md) ｜ 预计用时 60 min
> 数字规则：标准规定的数值（如硬件度量目标）以标准原文为准，本课不列具体数值；案例数字均为**教学示意值**。

## 1. 为什么需要"流程"

功能安全（Functional Safety。ISO 26262 语境：不存在由电气/电子系统功能异常导致的不可接受风险）有三个反直觉之处：

1. **安全不是功能，是属性**——过充保护是功能；"过充保护足够可信"才是安全。属性靠开发过程保证，所以这个学科是流程驱动的；
2. **严格度必须分档**——把所有部件都按最高标准开发，成本不可承受。ASIL 分级就是"按危害大小定开发严格度"的机制；
3. **必须留证据**——"我们很安全"不是论证；"我们按 X 级要求开发了 Y 并用 Z 方法验证了"才是。节点约束：**流程裁剪需留证据**。

## 2. 机制展开：安全生命周期与分级

**（1）安全生命周期三大段（ISO 26262:2018，S-07，共 12 个部分）**

- **概念阶段**（Part 3）：相关项定义（item definition，划定系统边界——正是 `SYS-02` 的活）→ HARA（`SAFE-02`）→ 安全目标 → 功能安全概念（FSC，Functional Safety Concept）；
- **开发阶段**（Part 4/5/6）：技术安全概念（TSC，Technical Safety Concept）→ 系统设计 → 硬件/软件开发；硬件配度量目标（Part 5），软件配验证方法（Part 6）；
- **生产与运行**（Part 7）：生产、运行、服务过程中的安全要求。

支撑部分：Part 2（安全管理）、Part 8（支持过程：需求管理、配置/变更管理、软件工具置信度等）、Part 9（ASIL 分解与安全分析）、Part 10~12（指南、摩托车、半导体适配）。

**（2）ASIL（Automotive Safety Integrity Level，汽车安全完整性等级）**

QM / A / B / C / D 四级+QM，由 HARA 的 S/E/C 三因子导出（下一课展开）。ASIL 决定：
- 分析深度：D 级通常要求 FMEA/FTA/DFA 全套相关分析（Part 9）；
- 软件验证严格度：结构覆盖率随 ASIL 提高而加严——**已核实（2026-11-13，ISO 26262-6:2018 §10.4.5 的公开转述源一致，S-69）**：标准用 "+"（推荐）/"++"（强烈推荐）标注而非硬性规定——语句覆盖 A/B 为 ++、C/D 为 +；分支覆盖 A 为 +、B/C/D 为 ++；MC/DC A/B 为 +、C/D 为 ++。**注意"ASIL A 只做语句覆盖"是常见的过度简化误传**；降低覆盖必须书面论证可行性缺口。
- 硬件度量目标（Part 5）：随机硬件失效指标（SPFM/LFM/PMHF，符号解释：单点故障度量/潜伏故障度量/随机硬件失效概率度量）——**目标值已核实（2026-11-10，公开来源见表；最终以标准原文为准）**：

  | 指标 | ASIL B | ASIL C | ASIL D |
  |---|---|---|---|
  | SPFM（单点故障度量） | ≥90% | ≥97% | ≥99% |
  | LFM（潜伏故障度量） | ≥60% | ≥80% | ≥90% |
  | PMHF（随机硬件失效概率） | <100 FIT | <100 FIT | <10 FIT |

  （FIT = 失效数/10⁹ 小时。注意：Part 5 将这些定为"高度推荐"的指导目标而非绝对要求；ASIL C/D 的评估通常配合 FTA。）

**（3）裁剪（Tailoring）**：允许按相关项特点裁剪流程活动，但**每项裁剪都要写论证并留证据**。这是"流程不是文档游戏"的关键：文档本身就是安全论证的载体。

## 3. 工程案例推演：拿"过充保护"走一遍概念阶段到开发落点

（评分与结论均为教学示意值，完整 HARA 推演见 `SAFE-02`）

| 步骤 | 产出物 | 本例内容 |
|---|---|---|
| 相关项定义 | 边界描述 | 电池系统及其与 VCU/OBC/热管理的接口（复用 `SYS-02`） |
| HARA | 危害清单 + ASIL | "快充中过充起火" → S3+E4+C3 → ASIL D（示意） |
| 安全目标 | SG-01 | 防止任一电芯超过充电电压上限 |
| FSC | 安全机制分配 | 主通道：BMS 检测过充 → 断开主正接触器；独立监控通道：独立监测电路冗余判定（分解为 B(D)+B(D)，见 `SAFE-03`） |
| 转入开发 | TSC | 把 FSC 落成系统架构与 TSR（`SYS-03` 的溯源链） |

后续开发阶段的严格度落点（示意，以标准原文为准）：
- 硬件：两通道各自完成安全分析，系统层验证随机失效指标；
- 软件：主通道过充判断软件按 D 级 → MC/DC 覆盖；监控通道按 B(D)；
- 确认（validation）：安全目标在整车层确认——故障注入 + 实车工况测试（`DEV-02`）。

## 4. 工程实态

- OEM 与供应商用 DIA（Development Interface Agreement，开发接口协议）分割安全活动责任（`SYS-03` 已提及）；
- D 级项目通常聘请独立的功能安全评估/审核（外部确认）；
- 裁剪的现实形态：成熟平台的 QM 功能套用既有流程；新 ASIL 功能做增量分析并留证；
- 与国标的关系：GB/T 38661（S-03）与 GB 38031（S-01/S-02）是**产品要求**（做出来什么样），ISO 26262 是**过程要求**（怎么保证做对）——两套都合规才算完整。

## 5. 常见误区

1. "功能安全=加个看门狗"——安全机制只是产出物，流程（分析、验证、证据链）才是学科本体；
2. ASIL 标在部件上——ASIL 是危害事件/安全需求的属性，部件经由承载需求获得等级；
3. 裁剪不留证据——审核时说不清为什么省略某活动，等于违规；
4. 把"流程走完"当"安全达成"——流程产出的安全机制还要在实车上有效，确认（validation）是另一回事。

## 6. 自测

**Q1**：为什么说"安全不是功能而是属性"？
**Q2**：FSC 与 TSC 的区别是什么？
**Q3**：流程裁剪的合法性条件是什么？

<details><summary>答案</summary>

- Q1：功能回答"做什么"（如断高压），属性回答"这份功能有多可信"（失效率、诊断覆盖率、验证严格度）。同一功能可按不同 ASIL 开发，可信度不同——因此安全靠过程属性而非功能有无来保证。
- Q2：FSC 在概念阶段，把安全目标分配到功能级安全机制（不绑定具体架构）；TSC 在开发起点，把 FSC 落到系统架构、接口与具体技术方案。
- Q3：每项裁剪都要有书面论证与留存证据（合规性证据），且不得削减安全目标所必需的活动。
</details>
