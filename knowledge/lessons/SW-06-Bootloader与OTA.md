# 课程 SW-06：Bootloader 与 OTA——升级失败不得致不可启动

> 对应节点 `SW-06`（[../domains/04-软件设计.md](../domains/04-软件设计.md)）｜ 前置：[SW-03](SW-03-通信协议栈.md)、[SW-05](SW-05-标定与诊断.md) ｜ 预计用时 60 min
> 数字规则：文中具体数字凡未挂标准/来源者均为**教学示意值**。

## 1. 为什么 OTA 是"整车的手术"

修 Bug 不召回的前提是升级绝对可控。节点约束点题：**需满足 UN R156（S-15）；签名校验与失败回滚；升级失败不得致不可启动**。BMS 的特殊性在于：它是高压安全的仲裁者——升级中继电器状态、保护功能不可处于半新半旧的混乱状态；升级失败若是"变砖"，售后成本与安全风险都不可接受。

## 2. 机制展开：分区、校验、回滚逐个看

**（1）Flash 分区（A/B 双分区方案，教学示意 2 MB）**

| 分区 | 大小 | 作用 |
|---|---|---|
| Bootloader | 128 KB | 最小可信基座，**自己永远不被 OTA** |
| Slot A | 832 KB | 当前运行固件 |
| Slot B | 832 KB | 新固件下载/验证区 |
| NVM（标定/自适应数据） | 64 KB | 掉电保存，版本迁移要考虑 |
| 参数区（RXSWIN/版本号） | 32 KB | UN R156 要求的软件识别号（RXSWIN）等 |
| 余量 | 160 KB | 磨损均衡与扩展 |

合计 128 + 832 + 832 + 64 + 32 + 160 = 2048 KB ✓

**（2）升级流程（UDS 刷写三段式，S-09）**：0x34 RequestDownload → 0x36 TransferData（多帧）→ 0x37 RequestTransferExit；全程要求扩展会话 + 0x27 鉴权（[SW-03](SW-03-通信协议栈.md)/[SW-05](SW-05-标定与诊断.md)）。

**（3）校验三层**：传输完整性 CRC → **签名验签**（非对称签名，公钥内置于 Bootloader）→ 版本号防回滚（防"用旧漏洞版本覆盖新版本"的攻击）。只验 CRC 不验签名是网络安全硬伤（ISO/SAE 21434，S-08）。

**（4）回滚（Rollback）**：新固件首次启动进"验证模式"，跑过 CRC + 自检后 Bootloader 才切换"确认"；启动失败计数器连续 N 次（示意 N = 3）未过验证 → **Bootloader 自动指回 Slot A**。关键纪律：Bootloader 保持最小化、代码路径简单——它是"唯一不可升级的裁判"。

## 3. 手算实例：升级时间与回滚预算

**传输时间**（教学示意值）：Slot B 832 KB，CAN FD 2 Mbit/s，协议与 STmin 开销按 50% 有效吞吐 → 有效 1 Mbit/s = 125 KB/s：
t_传输 = 832 ÷ 125 ≈ **6.7 s**

**编程时间**：Flash 写入速度 64 KB/s（示意）→ t_编程 = 832 ÷ 64 = **13 s**

**校验**：CRC 全区 + 验签 ≈ 3 s（示意）→ **总时长 ≈ 23 s**（不含整车进入升级模式的准备时间）。

**回滚预算推演**：13 s 编程中任意掉电 → Slot B 不完整，CRC 失败 → 启动仍走 Slot A ✓（A/B 方案的本质优势：**新固件写满并验证通过前，Slot A 始终是退路**）。对比"就地升级 + 备份压缩包"方案：备份与写入共享 Flash 寿命，且"写一半断电"的窗口处理复杂得多——车规倾向 A/B（示意工程共识）。

## 4. 工程实态

- UN R156（S-15）：软件升级管理体系（SWUP）+ RXSWIN 软件识别号，主机厂流程侧与零部件技术侧都要过审；ISO 24089《道路车辆 软件更新工程》提供工程方法框架；
- 整车级协调：升级条件（车速为 0、非高压上电态、电量满足）、多 ECU 升级的依赖顺序与失败联动由整车 OTA 主控决定，BMS 按请求执行并如实上报 RXSWIN/版本；
- NVM 迁移：新版本数据结构变化时要有迁移例程；**回滚后旧版本读不懂新 NVM** 是经典坑——NVM 结构变更需兼容版本号；
- 差分升级（delta OTA）省带宽，但对校验逻辑要求更高（合成结果也要全量 CRC + 签名验证，示意原则）。

## 5. 常见误区

1. 给 Bootloader 本身做 OTA——裁判下场踢球，失败即整车不可启动（UN R156 不可接受）；
2. 只验 CRC 不验签名——攻击者可伪造固件包（21434，S-08），CRC 只防误传不防篡改；
3. 忘记 NVM 版本兼容——升级成功但运行即崩溃，或回滚后读错数据；
4. "确认切换"前就清空 Slot A——退路没了，掉电即变砖，直接违反节点约束。

## 6. 自测

**Q1**：若 Slot 大小改为 1 MB、写入速度不变，编程时间多少？总时长受传输还是编程主导？
**Q2**：为什么版本号要防回滚？和签名是什么关系？
**Q3**：新固件启动后"验证模式"要验证什么才算"确认"？

<details><summary>答案</summary>

- Q1：1024 ÷ 64 = **16 s**；传输 1024 ÷ 125 ≈ 8.2 s < 编程 16 s → **编程（Flash 写入）主导**——提升 CAN 速率收益有限，Flash 编程速度才是瓶颈。
- Q2：签名保证"包是真的"，防回滚保证"包不旧"——两者缺一，攻击者重放旧签名包即可复活已知漏洞（降级攻击）。
- Q3：至少：CRC 完整性、签名已验、关键自检（存储、通信、安全机制）通过、与应用版本/标定兼容性检查通过，然后才置"确认"标志。
</details>
