# 课程 CHG-05：车桩匹配与即插即充

> 对应节点 `CHG-05`（[../domains/07-充电.md](../domains/07-充电.md)）｜ 前置：[CHG-02](CHG-02-充电通信协议.md) ｜ 预计用时 35 min
> 数字规则：文中时序与耗时均为**教学示意值**；证书体系沿 ISO 15118（S-10）框架描述。

## 1. 为什么"插枪即充"不简单

传统充电认证：刷卡 / APP 扫码 / 输密码——身份属于"人"，操作繁琐，且存在卡盗刷、二维码被覆盖等攻击面。

即插即充（PnC，Plug & Charge）：**身份与授权内置于车**——插枪瞬间，车用密码学证书向桩证明"我是谁、谁替我付钱"，全程无感。这是充电体验的终局形态，但依赖一整套 PKI（Public Key Infrastructure，公钥基础设施）证书体系——正是节点约束说的"依赖 ISO 15118 证书体系；桩端支持率是落地瓶颈"。

## 2. 机制展开

**（1）证书角色分工**（ISO 15118 框架，S-10）：

| 证书 | 持有方 | 作用 |
|---|---|---|
| V2G Root CA | 行业信任锚 | 全体系信任根，预置在车与桩 |
| Contract Certificate（合同证书） | 车辆/用户 | 证明"有权充电 + 计费账户"，含公钥 |
| OEM Certificate | 车厂 | 设备层身份 |
| 桩侧运营证书 | 桩/运营商 | 证明桩合法 |

**（2）即插即充流程推演**（步骤语义沿 ISO 15118，耗时为教学示意值）：

1. 物理连接 + **SLAC**（Signal Level Attenuation Characterization，信号衰减匹配，建立 PLC 链路，ISO 15118-3）：~2~3 s；
2. TCP/TLS 会话建立（双向认证、交换证书链）：~0.3~0.5 s（假设 RTT 50 ms 量级，示意）；
3. `PaymentDetailsReq/Res`：车出示合同证书链：~50 ms 级；
4. `AuthorizationReq/Res`：车用合同证书**私钥**签名挑战，桩/后台验证——证明"持证者本人在场"（防证书复制）：~0.2~1 s（含后台在线校验）；
5. 参数协商 → 充电 → 结算记录绑定 EVCCID（车端通信控制器 ID）。

从插入到开始充电合计 **~3~5 s**（示意），与传统刷卡相当，但零人工操作。

**（3）私钥安全**：合同证书私钥必须存于 HSM（Hardware Security Module，硬件安全模块）/ SE（Secure Element，安全元件），不可导出——证书可以公开，私钥泄露即身份失窃。

**（4）证书生命周期**：有效期（1~3 年量级，示意）→ 到期在线更新（CertificateUpdate 流程）；失窃证书走吊销机制（具体报文名待核对）。

## 3. 工程案例：国内落地路线推演（工程现状概述，细节待核对）

- **GB/T 27930 没有证书体系**（[CHG-02](CHG-02-充电通信协议.md)），所以国内"即插即充"目前主流是**平台级变通**：车联网平台预绑定 VIN 与支付账户，插枪后识别 VIN → 平台授权。体验接近 PnC，但认证强度是"平台信用"，不是端到端密码学；
- **真正 PnC 的落地条件**：行业级 PKI（根 CA 运营方）+ 桩端证书栈支持 + 车端 HSM 与证书 OTA 管理——三者缺一不可，这就是"桩端支持率是落地瓶颈"的含义；
- 过渡期：车端同时支持 27930 + 15118 双栈（出口车型已是常态）。

## 4. 工程实态

- 欧洲 CCS 网络 PnC 支持率持续提升（ISO 15118-2 桩侧逐步铺开，具体渗透率待核对）；
- **ISO 15118-20 已核实（2026-11-23，S-92）**：2022-04 出版，为**替代而非扩展**——-20 与 -2 报文集不可互通，桩需双栈并协商回退（EU AFIR 推动落地）；新能力：真双向 V2G/V2H/V2L（DC 为主）、DC 动态充电、无线充电支持、TLS 1.3 + 新证书体系；
- 车端供应链新三件：EVCC（车侧通信控制器）+ SE 芯片 + 证书 OTA 管理平台；
- 计费合规：PnC 结算数据须满足计量认证与税务要求（国内特有约束）。

## 5. 常见误区

1. 把"免扫码充电"当 PnC——平台 VIN 绑定没有端到端密码学认证，安全模型完全不同；
2. 认为 PnC = 免费/自动优惠——认证与计费策略是两层，价格照常执行；
3. 忽略证书运维成本——到期、吊销、跨运营商互认是持续运营问题，不是一次性开发问题；
4. 把插枪慢归咎 SLAC——多数耗时在后台在线授权往返（流程第 4 步）。

## 6. 自测

**Q1**：AuthorizationReq 用私钥签名是为了证明什么？只出示证书为什么不够？
**Q2**：在 GB/T 27930 上做"真 PnC"缺什么？
**Q3**：合同证书在充电中过期，合理处理策略是什么？

<details><summary>答案</summary>

- Q1：证明请求方**持有**与证书公钥配对的私钥（防复制证书重放）。证书是公开的"身份证"，任何人都能出示；只有真正持有人能完成签名挑战——非对称认证的基本逻辑。
- Q2：缺证书体系本身：27930 是明文 CAN 报文，没有证书格式、信任链、密钥存储规范，也没有行业根 CA 与桩端验证栈——需要"通信协议 + PKI + 硬件"三层同时补齐。
- Q3：进行中的会话不受影响（授权在开始时完成）；下次插枪触发在线更新（CertificateUpdate）或降级到 APP 认证；运营方应在到期前推送证书 OTA。
</details>
