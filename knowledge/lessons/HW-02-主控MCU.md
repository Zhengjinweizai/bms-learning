# 课程 HW-02：主控 MCU 与冗余设计

> 对应节点 `HW-02`（[../domains/03-硬件设计.md](../domains/03-硬件设计.md)）｜ 前置：[HW-01](HW-01-AFE模拟前端.md)、[SAFE-04](SAFE-04-安全机制与FTTI.md) ｜ 预计用时 60 min
> 数字规则：文中具体数字凡未挂标准/来源者均为**教学示意值**，不是特定厂商实测数据。

## 1. 为什么主控 MCU 受 ASIL 约束

主控 MCU 是状态机（[SW-04](SW-04-状态机设计.md)）、SOC/SOP 算法（[ALG-01](ALG-01-安时积分与OCV校正.md)）和继电器驱动决策（[HW-05](HW-05-执行器驱动.md)）的宿主。它一旦算错而继续自信地输出，比"不输出"更危险——所以节点约束写明：**算力 vs 功能安全冗余（锁步核），MCU 选型受 ASIL 约束**（S-07）。

ASIL D 的继电器误闭合、误断开都可能是危害事件（HARA 分析见 [SAFE-02](SAFE-02-HARA.md)），因此安全相关处理通道必须有**硬件故障可检测**能力——这正是冗余设计的动机。

## 2. 机制展开：一台 ASIL 级 MCU 的安全部件逐个看

**（1）锁步核（Lockstep）**：两个相同的 CPU 核同拍执行同一指令流，比较器逐周期比对输出；不一致 → 立即报错进入安全态。代价：两份核面积，换来"指令流级"故障检测。注意它检测的是**硬件随机失效**，不防软件共因 bug（两核跑同一份代码）。

**（2）存储与总线**
- RAM/Flash ECC（Error Correction Code，纠错码）：单比特错可纠、多比特错可检；
- MPU（Memory Protection Unit）分区：算法、协议栈、监控代码互相隔离，防"越界写垮安全机制"。

**（3）模拟量监控**
- 时钟监控（CMU）：主时钟漂移/停振检测；
- 电压监控（Brown-out detector）：欠压时不允许"带病续跑"；
- 温度传感器：MCU 自身过温。

**（4）看门狗与程序流监控**
- 窗口看门狗：喂狗既不能太晚也不能太早（早喂 = 程序跑飞后恰好又跑回来）；
- 程序流监控（question/answer 式）：要求按预定顺序回答"挑战"，检测控制流错乱。

**（5）安全岛/安全外设**：关键 IO（如继电器驱动、AFE 接口）经带自检的 IO 模块，输出回路可回读校验。

## 3. 手算实例：CPU 负载预算与可调度性

设任务集（周期 T、最坏执行时间 WCET C，均为教学示意值）：

| 任务 | 功能 | T | C |
|---|---|---|---|
| τ1 | AFE 数据搬运与检查 | 1 ms | 0.15 ms |
| τ2 | 保护/控制环 | 10 ms | 1.5 ms |
| τ3 | SOC/SOP 算法 | 100 ms | 8 ms |
| τ4 | 诊断与记录 | 1000 ms | 20 ms |

**Step 1 — CPU 利用率**：U = ΣC/T = 0.15 + 0.15 + 0.08 + 0.02 = **0.40（40%）**

**Step 2 — 速率单调（RM）充分条件**：U ≤ n(2^(1/n) − 1)，n = 4：
U_max = 4 × (2^0.25 − 1) ≈ 4 × 0.1892 = **0.757**。U = 0.40 < 0.757 → 在"D = T、任务独立、全抢占"假设下可调度 ✓

**Step 3 — 工程含义**：40% 的名义占用看似闲，实际还要留中断上下文、抖动、降级模式（故障后任务变多）的余量——量产惯例是稳态占用控制在 50~60% 以内（示意经验值）。此外，锁步双核的**吞吐开销主要在同步与比较**，算力规划按单核算。

## 4. 工程实态

- 车规 ASIL 级 MCU 代表：带锁步核的 TriCore/AURIX 类平台（示意家族，具体型号待核对）；消费级 MCU 不能直接上车（温度/寿命/失效率数据缺失）；
- 架构常态：**安全机制与应用解耦**——监控代码独立于算法，违反即报警（监控概念参考 [SAFE-04](SAFE-04-安全机制与FTTI.md)）；
- 故障处理时间对齐 FTTI（Fault Tolerant Time Interval）：看门狗窗口、看门狗反应时间要按 FTTI 反推，不是拍脑袋；
- MCU 的 ASIL 能力由厂商《安全手册》（Safety Manual）背书，BMS 开发方负责按手册集成（S-07 的分工原则）。

## 5. 常见误区

1. "有锁步核就安全了"——锁步不防软件共因失效、不防电源/时钟共因，架构级共因分析（[SAFE-03](SAFE-03-ASIL分解.md)）不可省；
2. CPU 按 100% 负载设计——故障模式（记录变多、降级策略）会把负载顶上去，超期就是新的危害；
3. 把看门狗当唯一安全机制——窗口监控、ECC、MPU、自检是分层防线，看门狗只是最后一道；
4. 拿 QM 级 MCU 加软件看门狗凑 ASIL D——软件机制不能替代硬件随机失效的检测能力（S-07 原则）。

## 6. 自测

**Q1**：τ2 的 WCET 若涨到 2.5 ms，U 变为多少？是否仍低于 RM 上界？
**Q2**：为什么窗口看门狗比"按时喂狗就行"的普通看门狗更强？
**Q3**：锁步双核运行同一份代码，哪类失效它管不了？

<details><summary>答案</summary>

- Q1：U = 0.15 + 0.25 + 0.08 + 0.02 = **0.50**，仍 < 0.757，但注意 RM 上界只是充分条件，最终要靠响应时间分析逐任务验证（见 [SW-02](SW-02-任务调度.md)）。
- Q2：普通看门狗只检测"没喂"，程序跑飞后若恰好周期性喂狗照样漏检；窗口看门狗额外检测"喂得太早"，配合问答式程序流监控可抓控制流错乱。
- Q3：软件共因失效（同一段代码的 bug 两核同错）、共因硬件环境（同一电源域/时钟源/温度应力）——需要架构多样性与共因分析补充。
</details>
